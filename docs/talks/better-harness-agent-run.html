Inside One Agent Run

Every message that passed between a harness and a small model while it answered one question, with notes on why each part is there.

The questionThe fuel-servicing checklist TO 00-25-172CL-5 points to one technical order for handling ESDS items. In that order, how far from the wire should the dry heat source be held when shrinking polyethylene tubing?

Answer
four to five inches, correct
Model
Qwen3.5-9B, 4-bit (fp4), Darkbloom through OpenRouter
Configuration
Grep Token Reduction + Thinking
Work
8 model turns, 9 tool calls
Tokens
41,948 input, 1,599 output
Cost and time
$0.0035, 179 seconds

Grep Token Reduction + Thinking has the highest median on the validation questions, 18 of 20 across 3 runs. On the test questions its median is 8 of 20, and the BM25 agent has the highest, 9 of 20. We captured this run on 3 November 2026 with fresh model calls, to record the full requests and replies, so it is not one of those three scored runs, and it ran on the earlier 222-page corpus of 68 files. The scores above are on the shared 531 pages, where this question was correct every time, using 4, 4 and 4 turns. One request hit a provider error (HTTP 522) and was retried; the model never saw that.

Question requires two hops

The checklist never mentions tubing, and the second file is named only inside the checklist. The model has to read one file, learn a name from it, and go and search another file. A single retrieval pass over the question’s words is unlikely to make that jump.

  1. Harness builds a requestSettings, tools and every message so far.
  2. Model repliesReasoning, then tool calls or a final answer.
  3. Harness runs the toolsPlain code, which adds hints and counts.
  4. Results join the messagesNext request holds them, until the model submits.

Fixes temperature at 0. The same input should give close to the same output. Differences between runs are then easier to read.

Raises the output limit. Reasoning counts against the limit of 16,384 tokens. At 4,096 the model could spend the whole limit reasoning and write no reply.

Pins the provider. With no fallbacks, every call uses the same 4-bit weights. A silent switch would change what we measure.

<file_format>
Each file is Markdown converted from selected pages of a document. A <!-- page N --> line marks the start of a page.
Files hold only some pages of the original, so a page number printed in a table of contents is not a line number and
is not a page marker. Use search or outline to find line numbers.
</file_format>

Prevents a known loop. An earlier run read “Table of Acronyms 140” in a contents page as line 140 and looped until its budget ended. This section exists because of that trace.

System message · <reply_economy>

<reply_economy>
Each reply resends the whole conversation, so fewer replies cost less. Send every call you can already foresee in one
reply: several searches together, then several reads together. To read several pages of a file, make one read call with
pages=[2, 3, 4]. Do not read pages one at a time.
</reply_economy>

Requests batched calls. Each turn resends everything, so the prompt asks for several calls in one reply. Turn 2 follows this rule.

System message · <procedure>

<procedure>
1. Choose files from the catalogue by title. When the question names a document, work inside that file only.
2. Search short terms of one to three words, written as the document would write them. A document in another language
   needs search terms in that language; translate names and technical terms before searching.
3. When the question names a section, call outline, then read that section.
4. Read around every useful hit. A matching line is rarely the whole answer.
5. When the question has several parts or names several sections or documents, read each one before answering.
6. When the question asks which documents match, search two or three phrasings with mode="count", then check every
   candidate file. Stopping at the first hit misses the others.
7. When the question asks whether something exists, a related but different thing does not count. Search several
   wordings, read the likely clauses, then answer "No, ..." if it is absent.
8. Stop calling tools once you can support the answer, then reply with the final JSON.
</procedure>

Sets the search method. This section gives the search method in numbered steps. Step 4, “read around every useful hit”, drives turn 6.

System message · <final_answer>

<final_answer>
Reply with only this JSON object:
{"answer": "<short answer in the document's exact wording>",
  "files": ["<path from the catalogue>"],
  "found": "yes" | "no" | "not_found",
  "evidence": [{"file": "<path>", "line": <number>, "quote": "<words copied exactly from that line>"}]}
- "files" lists every file that supports the answer. A question asking which documents match lists every match.
- "found" is "yes" when you found the answer or the thing asked about exists, "no" when the documents show it does not
  exist, and "not_found" when you searched thoroughly and the documents do not contain the answer.
- "evidence" holds one short quote for each part of the answer.
</final_answer>

Defines the answer shape. “evidence” requires one quote per part of the answer. The harness can check those quotes without a model.
